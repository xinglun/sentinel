# 開発実行プロトコル (Development Protocol)

本ドキュメントは、Stock Sentinel プロジェクトにおけるコードブランチのメンテナンス、実行成果物の取り扱い、およびマージ・リリースの原則を定義します。

## 1. コードブランチの取り扱い原則

- **`main` / `develop`**: コード、ワークフロー、ドキュメント、テスト、および標準設定のみを保持します。
- **実行成果物**: コードブランチへの混入を厳禁します。
- **ローカルの残存物**: 実行成果物をローカルの作業領域に長期間放置せず、コミット前に必ずクリーンアップしてください。
- **アーカイブデータ**: 実行により生成されたすべてのレポートおよびデータは、`data` ブランチにのみ保持します。

## 2. コミット前のクリーンアップフロー

コードをコミットする前に、必ずローカルで生成されたファイルを削除し、作業領域がクリーンであることを確認してください。

**クリーンアップすべき代表的なディレクトリ/ファイル:**
- `reports/**` (`.gitkeep` を除く)
- `backtest/*.csv`
- `backtest/summary.md`
- その他、実行時に生成される `.json` / `.jsonl` / `.csv` / `.md`

**目標:**
- 実行成果物をコードコミットに含めない。
- ローカル作業領域に古い実行残存物を蓄積させない。
- メンテナンス性と変更の可読性を向上させる。

## 3. ベースラインチェック要件

実行成果物のクリーンアップ完了後、以下のベースラインチェックを実行してください：
- `make test`
- `make clippy`
- `make fmt-check`

## 4. コミットおよびマージフロー

1. **変更のコミット**: ベースラインチェックを通過したことを確認後、`src/**`、`.github/workflows/**`、`docs/**` などのコアな変更を開発ブランチにコミットします。
2. **プッシュと PR**: 開発ブランチをプッシュし、通常の PR / Merge フローに従って `main` ブランチにマージします。
3. **開発への切り替え**: マージ完了後、速やかに `develop` ブランチに切り替えます。

## 5. データブランチ (data) の取り扱い原則

- **分離処理**: `data` ブランチをコードの PR と混ぜて処理しないでください。
- **自動トリガー**: コードが `main` にマージされた後、GitHub Actions ワークフロー (`daily_radar.yml` / `weekly_backtest.yml`) が自動的に新しいアーカイブを `data` ブランチにプッシュします。
- **履歴のクリーンアップ**: `data` ブランチの履歴ファイルをクリーンアップする必要がある場合は、`data` ブランチで個別にクリーンアップコミットを行い、コードブランチには混ぜないでください。

## 6. コア哲学

コードブランチは常にクリーンに保ち、実行成果物はローカルに滞留させず、アーカイブデータは `data` ブランチのみに集約します。
